# T7.59.2 — gate health workers until complete startup

Corrected the partial-thread-creation deadlock reproduced in `2bfd7736`. The
change is restricted to worker startup synchronization. The separate T7.59
array-bound scanner finding retains its unresolved disposition.

## Ownership and behavior

Each initialized worker has a startup-ready predicate protected by its existing
mutex. A new thread waits on its existing condition until either that predicate
is published or running becomes false. The start function resets the predicate
before creating each worker, creates all four workers, publishes started/stats,
then opens every gate. Only after full creation can a worker enter collection,
which may acquire lifecycle_lock.

On partial creation failure, startup still owns lifecycle_lock. It clears
running, signals each previously created worker and joins it. A gated worker
exits before entering collection, so it cannot wait for the mutex held by its
joining owner. The same initialized runtime remains retryable. No lock is
released during transitional startup ownership; concurrent start/shutdown calls
remain serialized by the existing lifecycle mutex. The gate uses a predicate
loop, so a wakeup alone does not authorize collection.

## Tests first and preserved RED

The original five-case producer and its **3 genuine timeout failures** remain
recorded in `build/eng-artifacts/T7.25.3/native-e7a616510df5/` and T7.59.1 evidence.

Before production edits, the fixture was strengthened to nine cases. The
handshake accepts either the original lifecycle-lock entry or the new actual
startup-condition wait. Both boundaries are observed on real threads; no worker
tier or runtime field is changed by the seam. On unchanged production every
failure still reaches the original lifecycle-lock boundary. This adaptation
allows the fix to prevent that obsolete interleaving without demanding that a
corrected worker enter the deadlock again.

Four new cases queue a real concurrent start or shutdown at lifecycle_lock while
the original start still owns it, for both partial failure and successful full
creation. A handshake proves that the contender reached that mutex before the
creation phase proceeds. Contenders are joined explicitly. Every worker thread
identity is tracked; successful joins must account for each created identity
exactly once, including same-runtime retries. Fake collectors and disabled
hardware/builtin providers avoid actual collectors or services.

## Separate pre-existing lifetime concern

Read-only review identified a different shutdown/reinitialization window:
shutdown clears global runtime and releases lifecycle_lock before joining
workers and destroying the global provider registry. A new init could reset and
register a new registry in that interval, which the older shutdown could later
destroy. This hypothesis was reported to the coordinator for a separate bounded
producer. The startup gate does not alter shutdown ownership or claim to fix
concurrent reinitialization/global-registry lifetime. The tested concurrent
start/shutdown cases do not introduce a new init while teardown is in flight.
