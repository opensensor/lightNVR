# T10 — Lint identity and typed AST compatibility

Implemented the lint foundation; full lint closure is explicitly assigned to
T10.1–T10.3 because the stronger detector exposed 21 existing untranslated
attribute/interpolation literals. T14/T15 and overlapping T7 repair owners must
wait for the appropriate children; no allowance was enlarged to conceal them.

## Changes

- Existing baseline keys are canonicalized by removing only `.js`, `.jsx`, `.ts`
  or `.tsx`. Allowance counts remain byte-for-byte unchanged. Duplicate canonical
  baseline keys fail configuration instead of creating two allowances.
- A first-party source identity may have only one implementation. A temporary JS
  sibling is permitted only with `@ts-check`, no suppression directives and a
  body composed solely of re-exports from its same-name typed sibling. The
  migration/typecheck integrator must still ensure each bridge participates in
  compiler checking; the lint rule proves bridge structure, not tsconfig coverage.
- TS expression wrappers, visible attribute expressions, nested template
  interpolation, array children and sequence results are inspected for visible
  strings. Translated calls and non-visible API/class attributes remain outside
  this intentionally syntax-based rule. This is not whole-program string-flow
  analysis.
- TS/TSX first-party modules now enforce hooks ordering/dependencies,
  accessibility, explicit-any bans and TS suppression bans as errors. Inline
  ESLint configuration cannot turn these checks off in migrated source. Legacy
  accessibility warnings remain explicit.

## RED → GREEN evidence

`node --test tests/quality/lint-compat.test.mjs` initially had **23 failures out
of 27**: rename allowance, typed children/attributes, hooks/a11y severity, type
escapes and duplicate-source cases. Four preserved-behavior controls passed.
The first implementation reached 26/27; the checked bridge control caught use
of an unavailable parser method (`parse` instead of `parseForESLint().ast`).
Correcting that reached 27/27 without weakening the control. An additional test
then proved inline `eslint-disable` could bypass migrated type enforcement;
`noInlineConfig` fixed that final RED case. Final result: **28/28 passing**.

Raw logs: `build/eng-artifacts/T10/{red,red-inline,green}.log` (ignored).

inspection, not new UI edits. The ten affected files, exact literals and lines

in `quality/evidence/T10-expansion.md`. T10's lint integration is not yet green.
