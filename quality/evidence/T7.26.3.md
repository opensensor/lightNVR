# T7.26.3 — bind verified migration bytes through publication

Filesystem copies now hash the held temporary descriptor, check its regular-file
identity/size/mtime before and after hashing, and retain that descriptor through
the database commit. The temporary pathname is moved with atomic no-replace
semantics into a newly created, verified, owned 0700 directory. The entry inside
that private directory must match the verified descriptor before it can be
published. A replacement is rejected before recording metadata changes. Its
entry is restored without replacing a concurrent entry; failed restoration
preserves and logs the private object for inspection. All no-replace operations
use guarded SYS_renameat2, with conservative failure on unsupported platforms or
filesystems and no unsafe fallback.

Publication uses the held parent directory. Immediately before committing, the
held file, named destination and parent pathname must still match the verified
snapshots. Cancellation and commit failure for this newly published filesystem
copy preserve the destination rather than unlinking a name that may have been
substituted. Source metadata and original bytes remain available on rejection.
Every opened file/parent/private directory descriptor is released on its handled
exit path. Normal move, copy, checksum, target guards and source cleanup controls
continue to pass.

The original producer's rejection/source-location/verified-object assertions are
unchanged. Its deterministic seam now substitutes the public temporary entry
immediately before the post-verification quarantine rename, the corresponding
identity-binding boundary. Before production edits, native-ee5def20588c ran 23
cases with two failures: that original substitution and a new published-file
replacement at the committing-state update. Unsupported quarantine operation
was also exercised. Direct test production was authorized because no separate
worker slot was available.

Fault review added restoration collision, cancellation substitution and failed
DB-commit substitution controls. The restoration test exposed a draft cleanup
accounting bug (native-82108ffa05d1: 26 cases, one failure): an unrecognized
private-directory name allowed cleanup to claim success. Private staging names
now carry the job-associated prefix. The same assertion proves the directory
and unverified entry survive and cleanup remains pending even after the
separate test-created restore-collision entry is removed. Additional controls
reject mutation of the verified inode and parent replacement even when the
replacement parent contains a hard link to the same file inode.

Limits are deliberate and material. The final identity check and SQLite commit
are not one atomic operation: arbitrary replacement after that check remains a
window. A same-UID/privileged actor can modify the private namespace, and a writer
already holding the inode can modify bytes; this does not establish universal
concurrent-writer safety. Existing-destination reconciliation, S3 restore/upload
identity and source-unlink identity are outside this child. No fresh scanner
result, risk acceptance or baseline approval is claimed; reconciliation remains
T33.

Private-directory removal is best-effort, empty-directory-only and never
recursive. Its identity check followed by rmdir is not atomic against replacement
of the parent entry. On failure, the retained location is logged. Failed jobs'
job-associated directories are recognized by abandoned cleanup and keep debt
pending. If publication succeeds but removal of its now-empty private directory
fails, the completed filesystem job is not selected by abandoned cleanup: that
empty-directory debt is logged for operator inspection, not persistently tracked
or automatically reclaimed. Successful publication therefore does not imply
that every staging directory was removed.
