## Existing boundaries and at-rest limitations

The database list/get projection selects `(password<>'')` rather than password; its DTO has a boolean `password_configured` and no password field. API create/get/list/update serialize that DTO and audit metadata. Every destination handler calls `AUTHZ_EVENTS_CONFIGURE` before parsing/mutation; the tests enable authentication and exercise default roles. This is action-based authorization, not a claim that no custom-granted role can configure destinations. Authentication-disabled configuration is not qualified by those controls.

The sole production caller of `db_event_destination_get_password` is `mqtt_destination_client_create`. It requests the exact profile revision, passes the returned password to `mosquitto_username_pw_set`, and securely zeroes its stack buffer on success and failure paths. The runtime getter zeroes the supplied output before validation and refuses stale/missing/invalid/too-small requests. Revision matching is a consistency check, not local-process authorization or encryption; any trusted in-process caller with database access can query the value.

`db_core.c` opens ordinary SQLite, while `db_backup.c` copies ordinary SQLite through its backup API. No encryption key/provider is configured in these paths. Filesystem access therefore governs access to database, WAL/journal and backup contents. The private test uses a unique 0700 directory and umask 077 with a 0600 database; those are fixture controls, **not evidence that every deployment uses those modes**. Application database creation inherits filesystem/umask behavior; storage-class encryption or protected volumes are not established by this source review.

An irreversible hash cannot replace the stored secret: MQTT authentication requires recovering the credential. Encrypting it safely requires a defined custody/provider, bootstrap, unattended restart, missing-key behavior, rotation, backup/restore and upgrade/downgrade policy. A hardcoded key, key stored alongside the ciphertext/database, or merely renaming/encoding the field would not resolve the established exposure. Clearing/replacing a logical value also does not establish physical erasure from historical database pages, WAL or backups.
