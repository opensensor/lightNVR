# T7.175 — meaningful control names and visible label associations

Resolved all 11 mapped control-has-associated-label occurrences across the three
owned components. No translations, dependencies, lint suppressions, hidden
labels, baseline or policy exceptions were added.

- RoleManager uses stable Preact useId-based IDs, native label htmlFor/input id
  relationships and aria-labelledby references to the existing visible labels.
  Name/description use their existing translations. Permission checkboxes use
  the existing visible permission identifier as their name; descriptions and
  destructive/not-enforced messages remain available through aria-describedby.
  Built-in-role disabled states and checkbox callbacks are unchanged.
- TOTP's existing visible QR wrapper is exposed as a named image using the
  existing scan prompt. Its pixel canvas is decorative within that named image;
  the existing manual-secret fallback remains visible and accessible. The
  verification input now has an actual native association with its visible
  translated label plus an explicit aria-labelledby reference. Input filtering,
  autofocus, required state and submission callbacks remain unchanged.
- Each of the five UsersTable icon buttons has an aria-label from its existing
  translated tooltip key; tooltips remain. SVGs are decorative within their
  named buttons. The sixth mapped occurrence is the surrounding action cell:
  its actual named button descendants now satisfy the scanner's label traversal,
  without inventing a cell label or changing table semantics.

## Tests first and implementation details

The raw T1 JSX report is
`build/eng-artifacts/T1/actions/static-analysis-41176542849/web-jsx-a11y.log`.
Fresh full lint before changes reproduced all 11 occurrences. Test file
`web/tests/remediation/t7_175.spec.jsx` was written first. Its initial Node run
failed all four cases (`build/eng-artifacts/T7.175/jest-red.log`); the initial
actual-Preact browser run also failed the expected precise permission name
(`browser-red.log`). Existing implicit labels already provided some browser
names, but did not establish the explicit relationships required by the scanner;
this evidence does not claim those fields were previously entirely unnamed.

The tests inspect and interact with the real components. Node checks verify
visible label references, native associations, preserved disabled states,
permission help, verification filtering/submission, and all five original
user-action callbacks. The actual Chromium mount verifies native label clicks,
checkbox Space activation, built-in disabled fields, QR image naming and
verification Enter submission. It removes icon-button title attributes before
locating each named button, proving names do not rely on tooltip fallback;
Enter and Space each dispatch exactly once to the original user callback.

A first implementation attempted role=img directly on canvas, but the configured
rule set reported a new interactive-element/noninteractive-role warning.
The final representation names the existing visible image wrapper and keeps its
canvas pixels decorative inside it, matching the rendered graphic. An isolated
Chromium probe also showed that a blank canvas with only aria-label has no
exposed image role. The [ARIA in HTML guidance](https://www.w3.org/TR/html-aria/)
was consulted while resolving this representation; no new warning is accepted.

Intermediate test-fixture corrections are retained in browser-green.log and
browser-second.log: Preact/compat normalizes text onChange into oninput, and the
mock verification counter initially incremented only when a JSON body was read
(the real success path correctly does not read one). Neither is claimed as a
product defect. The final combined run verifies the original boundary suite too.

Coordinator authorized exactly one additional path: t7_165.spec.jsx received a
mechanical useId mock entry so its existing Node boundary assertions still run.
No assertions in that earlier suite were changed. Its browser portion continues
to use actual Preact hooks, not the mock.
