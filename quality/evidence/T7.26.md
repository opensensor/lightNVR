`storage_migration_process_one()` claims a database job, resolves registered
source/destination targets and object keys, checks source mount availability and
destination probe/mount guard, then invokes `copy_and_verify()` for filesystem
transfers. That function holds a source descriptor during copying, writes a
temporary destination, fsyncs and closes it, independently hashes its pathname,
checks cancellation and destination absence, then publishes by ordinary rename.
The worker subsequently commits copy/location metadata and, for moves, verifies
the destination before deleting the source. Successful controls must preserve
these database and filesystem semantics.

The test uses unique private files and a disposable real SQLite catalog,
registered filesystem targets, and the public migration worker. Deterministic
filesystem seams insert a competing regular file or symlink after the final
absence check. Its atomic-publication seam can also insert the same object just
before `SYS_renameat2`, without relying on a timing-sensitive thread race. It
checks source and destination bytes and persisted recording location, alongside
ordinary move/copy and unavailable-source controls.

## Observed failures and bounded follow-ups

1. **Mapped publication race**: a regular destination created after the final
   absent check is overwritten by source bytes. A symlink created in the same
   window is also replaced. Its target bytes remain intact; this is entry
   overwrite, not symlink-target truncation. Both cases require atomic
   no-overwrite publication, failure before recording-location commit, and
   retention of the source and competing entry.
2. **Abandoned-cleanup ownership**: a preexisting unrelated destination causes
   the first worker pass to fail normally and preserves the source. The next
   worker pass's `cleanup_abandoned()` unlinks that unrelated destination despite
   the job never publishing it. This separate cause requires proof of ownership
   before cleanup or conservative retention/reporting when ownership is unknown.
3. **Verified-temporary identity**: after the temporary file is hashed, the seam
   renames that verified object aside and installs different bytes at its old
   pathname. The worker publishes the unverified replacement and changes the
   recording's target UUID/path to that destination. The original verified bytes
   remain in the fixture's held-aside file. This requires retaining/proving the
   verified file identity through publication and commit, not just preventing a
   competing destination from being overwritten.

These follow-ups have been proposed to the coordinator as separately ordered
children with exact source/test ownership. No unscoped fix or schema/storage
policy redesign was attempted. The temporary-substitution oracle currently
requires rejection before metadata changes; the child contract must explicitly
preserve this or authorize a safe alternative that publishes the held verified
bytes with matching metadata, never unverified data.

Ordinary verified move and copy pass. Move commits destination metadata and
removes the source; copy preserves source location and verified destination bytes.
An unavailable registered source root leaves bytes and location metadata intact
after restoring the disposable fixture root. Real target catalog/mount guards,
SHA-256 verification, state transitions and SQLite schema are used.
