# T7.25.1 — identity-preserving stale backup cleanup

The committed T7.25 parent/leaf replacement regressions now pass. Cleanup pins
the backup directory and candidate inode, atomically moves the entry without
overwriting into a verified private directory, and checks the moved object's
identity before unlinking. Changed objects are restored without overwrite or
retained with a logged quarantine location and an incomplete-cleanup result.
Changes are confined to `db_core.c`'s stale-cleanup helpers, fault-test seams and
this evidence. No schema, retention policy, database-open or restore logic changed.

## File ownership and failure behavior

The existing startup-only eligibility rules remain: recognized temporary backup
names, regular files, and writable database initialization. There is no new age
cutoff. `opendir` pins the enumerated parent; all candidate operations use that
directory descriptor. `O_PATH | O_NOFOLLOW | O_CLOEXEC` obtains a candidate
descriptor without following symlinks or opening/blocking on FIFOs/devices.
`fstat` selects regular files, and the descriptor remains open throughout cleanup,
preventing inode reuse after an attacker unlinks the inspected name.

For each eligible candidate, a DB-independent cryptographic UUID names a new
`.cleanup-<uuid>` directory, created relative to the held parent. Creation retries
at most four name collisions. The opened directory must match the checked
device/inode, belong to the effective runtime UID and have exactly 0700 access
bits. Inherited setgid does not grant group access and remains compatible.

Both the initial quarantine move and restoration use Linux `renameat2` with
`RENAME_NOREPLACE` through a **guarded `SYS_renameat2` syscall**, so a newer libc
`renameat2` export is not required. Neither operation has a check-then-overwrite
fallback. This protects unrelated data even if an already-populated, app-owned
0700 directory is substituted between directory creation and opening.

After the move, `fstatat(..., AT_SYMLINK_NOFOLLOW)` must match the held candidate's
device/inode, regular type, size and mtime snapshot before unlink. A mismatch or
unlink failure requests atomic no-overwrite restoration. If restoration fails,
including destination collision or unsupported syscall/filesystem, the object
remains inside quarantine; cleanup reports failure and logs its location. The
log resolves the held directory through `/proc/self/fd` when available, otherwise
reports the nominal path and directory identity, noting that its parent may have
moved. No recursive removal of retained objects or unknown crash leftovers occurs.

The pass stops at its first incomplete cleanup. A restored entry can otherwise
be revisited by directory iteration after mutation and mistakenly treated as a
fresh eligible file. Normal success removes only the inspected eligible file and
its now-empty private directory; every candidate/private descriptor is closed.

## Explicit limits

Without `O_PATH`, or with an unsupported candidate open, cleanup fails
conservatively without deleting the candidate. Without `SYS_renameat2`, or when
the kernel/filesystem rejects no-replace semantics, it does not fall back to
overwriting. Runtime ENOSYS/EINVAL failures are tested; older libc/kernel builds
were not executed. Failures before moving preserve the original file; failures
after moving can leave a logged quarantine requiring operator inspection.

A crash can leave either an empty private directory or its moved object. Future
startup scans deliberately do not recursively delete `.cleanup-*` leftovers.
Initial configured-parent symlink resolution is unchanged; this is not a general
filesystem containment policy or protection against a compromised runtime UID,
a privileged actor, concurrent writers already holding the file open, or multiple
actors able to modify the private directory. Size/mtime checks are snapshots,
not a writer lock.

Empty-directory removal retains a separate **best-effort** identity check followed
by `unlinkat(..., AT_REMOVEDIR)`. A mutable parent can replace that name between
those calls, so atomic identity of an empty directory is not guaranteed. That
operation is nonrecursive and cannot remove a file or nonempty directory. This
limitation is distinct from the protected file unlink inside the held private
directory, and is stated explicitly rather than claiming universal race freedom.
