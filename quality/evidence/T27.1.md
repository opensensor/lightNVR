## Ownership and behavior

The existing planned-path helpers keep their timestamp format and directory
layouts. They do not create a recording file. Immediately before the managed
reader calls `record_segment`, `reserve_mp4_recording_path` creates the final
pathname with `O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC`, retaining its open descriptor
through the synchronous segment call. An existing path is never opened/truncated
by reservation: bounded `_001`…`_999` suffixes are tried instead. All buffers and
placement constraints are checked before creation; failed allocation leaves the
caller's path and placement unchanged. No random-name collision probability or
racy `exists()` test is presented as exclusive ownership.

Successful reservation changes the writer's path and placement.object_key
together before the first-frame metadata callback. The ordinary unused
`recording_YYYYMMDD_HHMMSS.mp4` spelling, stream/date directories and `.mp4`
extension stay intact. The descriptor is released after the segment call. Only
a still-empty regular file matching the held device/inode is removed; written
media and replacement files survive. No pending reservation exists during the
initial writer allocation or pressure wait, and no startup/core lifetime API
changes are needed. `mp4_writer_create` allocates state but does not open/header-
write this managed-reader output path.

Retry now passes through normal prior-file finalization before preparing the
next output path. Previously it could change output_path while retaining the
prior metadata ID. Effective default duration is resolved **before rotation**;
zero/negative configuration values must not bypass that finalization. Buffer,
reservation and cleanup failures are explicit. Existing deterministic
forced-reconnect/backpressure tests retain their segment boundary seams; a new
focused target exercises real reservation files and concurrency.

The managed placement path already required absolute roots in
`build_mp4_recording_directory_at_root`; the reservation API does not narrow a
previously supported relative planned-path contract. Existing layout controls
cover flat/year-month/year-month-day, direct MP4 roots and buffer handling.
Playback/download and storage consumers use stored paths/object keys and the
extension, so no timestamp parser or schema rewrite is needed.
