native htmlFor/id association. Its existing translated text is in a dedicated
span referenced by aria-labelledby, so the accessible name does not include the
input itself. Text classes and spacing remain on that span; input classes,

from T7.175 (`359ade6d`); they received regression coverage without redundant

## Tests first

This task used direct tests-first work; no separate test-writer slot was used.
The new `web/tests/remediation/t7_187.spec.jsx` initially produced one Node
failure for TOTP's missing nested control, while the existing RoleManager
associations passed. `jest-red.log` records that precise result. The initial
actual Chromium run (`browser-red.log`) also found the duplicate heading ID:
21 elements had IDs but only 20 IDs were unique across four mounted modals.
Both failures preceded their production corrections.

The Node suite now asserts every label nests exactly its explicitly referenced
control and its visible naming node does not recursively contain that control.
The actual browser mounts two RoleManager and two TOTP instances in one Preact
root. It verifies all DOM IDs are unique, each dialog references its own heading,
all eight labels resolve to exactly one control in their own instance, every
label-text click focuses its intended control, and each permission label changes
its checkbox once. Field edits and a parent rerender retain IDs and associations;
a second-instance label still focuses the second instance. Label actions never
dismiss a modal. The earlier T7.165 and T7.175 browser suites additionally retain
saving guards, native keyboard actions, built-in-role disabled controls and TOTP
verification submission behavior.

One intermediate browser fixture failure (`browser-green.log`) was caused by
passing a new getAuthHeaders function on the synthetic parent rerender. That
correctly retriggered the component's status-fetch effect and replaced the setup
view. The fixture now keeps that callback stable to isolate ID persistence;
no application behavior was changed to accommodate the test. Browser bundles
use actual Preact/components; only external service, i18n and QR drawing adapters
are fixtures. No backend server or live API is used.
