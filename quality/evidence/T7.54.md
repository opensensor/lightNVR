## Buffer and caller trace

`get_json_logs()` opens the configured log file, rejects negative `ftell`, caps
the nonnegative requested read at 100 × 1024 bytes, returns early for an empty
file, and allocates `read_size + 1` bytes. `fread` receives that bounded request.
Even an unexpectedly larger return value is explicitly clamped to `read_size`
before termination. The valid terminator index is therefore 0..102400 in a
buffer whose allocation includes that byte. Short reads use their actual count.
Newline scanning and the final-line check remain within `bytes_read`; the latter
checks nonzero length before subtracting one. There can be at most 102400 counted
lines in this bounded input, so the subsequent int counter and pointer-array
allocation cannot grow from an unbounded file size.

The function owns and frees its read buffer and file. On success the caller owns
the returned array and duplicated lines, including a possible empty array after
filtering; on allocation failure partial lines and buffer are freed and the
initialized outputs remain null/zero. Caller parameters are expected to be valid
output pointers and a nonnull level string. No null-parameter contract change was
inferred or introduced.

Search of current `src` finds no production caller of this legacy reader. The
active system-log endpoint calls a different function, `get_json_logs_tail()` in
`api_handlers_system_logs_tail.c`, whose behavior is outside this task. The write
side is invoked by `logger.c`: its existing 4096-byte formatted buffer passes a
terminated, at most 4095-byte message to the JSON writer. Direct JSON writes use
cJSON serialization, including optional thread component/stream fields.
