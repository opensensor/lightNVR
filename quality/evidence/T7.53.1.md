# T7.53.1 — available storage fixture for authorization controls

The sensitive-handler authorization test now creates a private available legacy
storage root and places its three synthetic recording paths beneath that root.
It still requires exact HTTP **200** and removed metadata for authorized direct
deletion, exact **403** and retained metadata for forbidden deletion, and exact
**202** plus eventual metadata removal for asynchronous batch deletion. No
production code or expected status was changed.

## Established failure and cause

T7.53's broader ASan/UBSan run (`native-51cb288c8065`) failed the existing test at
its direct DELETE assertion: expected 200, received 202. The response body leaked
83 bytes because `call_handler_path()` asserted status before freeing it. The
exact pre-T7.53 authorization implementation produced the same result in
`native-2d47cc11c188`; logs for both are preserved under
`build/eng-artifacts/T7.53/`, with 33/34 authorization cases passing.

The old fixture used fixed paths directly under `/tmp` without establishing an
available configured legacy recording root. Its files are deliberately absent
because download tests require 404/409. `storage_deletion.c` treats a missing
unattributed file as authoritatively absent only if it lies below an available
configured root (`legacy_missing_path_is_authoritative()`). Otherwise deletion
remains retryable, and the backend-agnostic handler correctly returns 202.
The observed handler acceptance log and 202, combined with this unchanged source
path, identify a missing fixture precondition rather than a permission regression.
The coordinator materialized this bounded test-only follow-up before edits.

## Repair and cleanup

Only the sensitive-handler case creates the unique `mkdtemp` directory. It sets
`g_config.storage_path` to that directory, uses paths beneath it for allowed,
denied and batch recordings, and creates **no video files**. Existing download,
protection, audit, ownership and deletion assertions remain unchanged.

Setup snapshots the previous storage path. Unity teardown restores it and removes
only the owned empty directory with `rmdir`, including after a test assertion
unwinds the case. Config restoration occurs before the cleanup-result assertion.
No recursive deletion or removal of unrelated `/tmp` paths is introduced.
`call_handler_path()` saves the actual status, parses JSON only on matching
status, frees the HTTP response, and then asserts status and parse success. Thus
a failed status assertion neither abandons a response nor a parsed JSON object.
