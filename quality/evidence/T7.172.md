## Separate existing bulk-tag state defect

The first broader regression run was **139 passing / one failing**. With stale
recordings props after adding a previously unknown tag, its checkbox can revert
unchecked. `addNewTag` sets local `tagStates` to all and updates `allTags`; the
`[allTags, selectedRecs.length]` effect recomputes states from the stale recording
props. The real RecordingsView bulk callback only invalidates the recordings
query, unlike the single-recording callback that updates local data immediately.
The effect also does not depend on the recording tag contents, so a later
same-length refetch alone need not recompute states.

This is outside the name-only production change and was reported to the
coordinator for a bounded follow-up. No tag logic was modified to hide it. The
same successful-new-tag checked assertion remains in the test. Its normal fixture
models delivered post-save recording data; an explicit stale-recordings mode
withholds that refresh and retains the desired assertion. The initial flaky pass
was made deterministic by waiting two animation frames before checking the new
checkbox. Both `bulk-stale-props-red.log` and `bulk-stale-opt-in-red.log` record
the genuine failure, independently of names:

```sh
T7_172_BROWSER=1 T7_172_STALE_REPRO=1 npm --prefix web test -- --runInBand \
  --testPathPatterns=t7_172 --testNamePattern='bulk tags retain mixed'
```

The normal fixture is not claimed to validate the real asynchronous parent/query
refresh path. The stale-data failure remains open; it is not an exception approval
or an assertion that accessibility naming repaired tag reconciliation.
