# T7.11.1 — proposed destination credential storage contract

Status: design delivered; **not approved or implemented**. CODEQL-316 and CODEQL-307 remain confirmed unresolved. No exception, key owner, expiry, physical qualification or implementation authorization is supplied by this document. T7.11 and its T33 closure requirement remain open.

The machine-readable proposal is [`../credential-storage-contract.json`](../credential-storage-contract.json). It records source hashes, exact data and key lifetimes, API behavior, failure cases, unresolved decisions and nine bounded implementation children. These children are proposals, not changes to the executable plan.

## Recommendation and existing constraints

Use versioned authenticated encryption for destination passwords with the already-required mbedTLS library and a dedicated, operator-provisioned, read-only regular keyring file outside application database/config/backup volumes. The selector contains only an absolute path. Do not generate a substitute key on failure. A private startup snapshot remains valid until shutdown; replacing/removing its file does not revoke an already-running process. Rotation of the master key initially requires an offline maintenance window.

The current database stores passwords in a TEXT column introduced by `db/migrations/0060_add_event_destinations.sql`. Both creation and replacement bind plaintext in `src/database/db_event_destinations.c`. Existing T7.11 characterization reproduced this with a real private database; redacted API responses and access controls do not resolve at-rest persistence. Runtime recovery requires the original password: `mqtt_destination_client.c` obtains it through the expected-revision getter and passes it to the MQTT library. The contract preserves this capability, authenticated API omission/clear/replacement semantics, revision checks, and client recreation after credential changes.

`CMakeLists.txt` already requires mbedTLS, and `src/utils/lpr_crypto.c` demonstrates GCM plus OS entropy and buffer zeroing. Its key and environment variable are LPR-specific; this proposal allocates a separate destination key. Existing code demonstrates available primitives, not qualification of a new feature or every embedded target.

Docker runs UID/GID 10001 and Compose separates configuration/database/recording volumes. The entrypoint preserves operator-mounted permissions. The installer instead produces a root-run systemd service and 0755 data directories. The proposed provider requires a private runtime-owned file outside these exported data roots, with explicit provisioning for each deployment. Existing deployment layouts do not establish a key-custody policy. T5 physical/older-kernel qualification remains deferred.

## Cryptographic and persistence basis

The proposed envelope uses a 32-byte key, 12-byte random nonce and 16-byte tag, binding a versioned domain, destination UUID and key ID as authenticated data. The library contract distinguishes tag-producing decryption from authenticated decryption; the proposal requires `mbedtls_gcm_auth_decrypt` and rejects authentication failure without returning plaintext. [Official mbedTLS GCM API](https://mbed-tls.readthedocs.io/projects/api/en/mbedtls-2.28/api/file/gcm_8h/).

The random-IV design requires a qualified entropy source, fresh nonces and a lifetime invocation limit. The proposal reserves durable attempt counts, burns counts on failed data writes, and requires a fresh active write key after restore/clone because restored counters can roll back. The proposed 96-bit random field and 2^32 invocation ceiling follow sections 8.2.2 and 8.3; a check against current rows does not establish deterministic uniqueness across historical invocations. No FIPS, hardware-custody or cryptographic implementation qualification is claimed. [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf).

Conversion of live rows does not erase historical bytes. SQLite documents limits on logical deletion and secure deletion, and VACUUM has transaction, locking and space requirements. Active readers can retain dependencies on WAL content. The proposal requires separate protected maintenance and raw artifact verification, never manual removal of live WAL or a claim that rewriting one database erases backups, snapshots or physical media. [SQLite secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete), [VACUUM](https://www.sqlite.org/lang_vacuum.html), [WAL](https://sqlite.org/wal.html).

## Observable behavior and compatibility

- Missing, malformed or inaccessible keys block credential writes and credential-dependent delivery with an explicit nonsensitive error. No default key, anonymous retry or legacy plaintext delivery is permitted. Recommended degraded startup keeps recording and metadata available; this availability choice remains D1.
- Omitted passwords preserve existing credential bytes and configuration state. Explicit null/empty clears the logical credential under existing authorization/revision checks. Replacement encrypts before database binding and uses the existing optimistic revision check; failed/stale updates preserve the old row.
- GET/list/audit remain redacted. A configured but locked password remains configured. Plaintext lives only in scoped runtime buffers and the MQTT client's required copy; caller buffers are cleared and superseded clients destroyed. This does not claim immunity to process compromise, swap or core disclosure.
- Rename the old password column and add versioned envelope constraints/accounting. Pending legacy values can survive a failed migration for recovery but cannot be used for delivery or newly written. Before workers start, convert the bounded set of at most 64 destinations atomically while preserving IDs, routes, outbox associations and representation-only revisions.
- A failed conversion preserves the old representation, blocked pending recovery. The recommended policy also blocks new database backups while plaintext migration is pending. Existing copies remain protected and inventoried, not silently deleted or called encrypted.
- Offline rotation verifies old credentials and atomically replaces their representation. Keep old decryption keys separately for retained backups. Restore always goes forward through the new implementation and uses a fresh active write key. Down migration refuses explicitly; old destination SQL fails after the column rename, but this alone does not promise an old entire binary refuses startup.

The threat model covers read-only disclosure of database/backup material when the separate key is unavailable and detects authenticated-record tampering/substitution. It does not cover privileged/runtime compromise, disclosure of both key and database, whole-database replay, hostile filesystem writers, historical plaintext copies or other classes of application secrets.

## Startup and backup ordering clarification

Source review confirms that `db_core.c` can recover from an existing backup before opening the main database, runs schema migrations, invokes `perform_database_backup_cycle("initial", true, true)` for a new database (currently line 1256), then releases the scheduled-backup hold. Scheduled and shutdown backups share the cycle function. The current implementation has no proposed credential-readiness gate.

Under D1 **if approved**, initialization begins with readiness unknown and normal backup/export admission closed. Attempt provider initialization, recover/open and structurally migrate the database, inspect credential state and finish required credential conversion, then publish migration-ready. Only afterward may the initial backup run and scheduled admission resume. A verified database with no pending legacy credentials may become backup-eligible without a usable provider; encrypted-but-locked destinations remain unable to deliver. An unknown schema or incomplete startup cannot establish absence of plaintext.

The same gate must cover initial, scheduled, shutdown and direct/manual backup/export paths, including failed startup and settings restart. Apply it before creating copy artifacts, changing latest-backup links, invoking hooks or pruning retention, and do not advance successful-backup timestamps on refusal. T7.11.5 owns initialization ordering; T7.11.7 additionally owns the `db_core.c` backup admission boundary, ordered after that integration child. Both remain proposals.

Existing recovery copies keep their actual plaintext exposure classification and remain available as protected forward-migration inputs. A *new* pre-migration safety copy would create another plaintext exposure, so its protected destination and recovery tradeoff must be explicitly covered by D1 before upgrade proceeds. It is not an automatic bypass of the gate. This design neither silently deletes existing recovery material nor silently suppresses a required safety-copy step; conflicting recovery requirements stop upgrade with an explicit unresolved-policy error. Logical migration-ready also does not establish that free pages/WAL are free of historical bytes; the separate raw-artifact checks remain necessary.

The added twelfth validation scenario covers valid/missing keys, recovery from a legacy fixture, partial conversion failure, restart and shutdown. It requires refusal before copy/link/hook/retention effects and successful-backup timestamps, preservation of existing recovery artifacts, and explicit treatment of any D1-authorized maintenance copy as plaintext exposure. D1 remains unapproved; no source changes or implementation validation occurred.
