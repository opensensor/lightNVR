## Design

**Expected reports.** Every scanner in `quality/scanners.json` must be accounted for. The report path is resolved in this order:
1. `report_pins` in the policy (scoped to one reports dir)
2. `run-manifest.json` `reports` in the reports dir
3. `report_path_convention`. `<sha8>` matches hex only and `<run_id>` matches digits only. `{all,prod}` expands to several required files. Trailing ` (...)` notes are ignored.

A pattern with 0 matches gives `missing-report`. If the scanner's `access_status` is `not-configured` or `disabled`, it gives `not-scanned` instead. A pattern with more than 1 match gives `ambiguous-report`; the checker never picks one.

**Normalizers.** Each one reproduces the T1 fingerprint scheme exactly (`scanners.json#fingerprint_schemes`):

| Scanner/format | Identity | Health/scope checks |
|---|---|---|
| CodeQL SARIF | `codeql:<rule>:<path>:<primaryLocationLineHash>` | `executionSuccessful=false` or an error notification gives `scanner-error`. A wrong `automationDetails` category gives `scope-mismatch`. Zero results need scope evidence. |
| Trivy SARIF | `trivy:<target>:<package>:<CVE>` | Missing `imageName`/`imageID` gives `empty-scope`. A different image gives `scope-mismatch`. |
| clang-tidy text | `line-tool` (rule\|path\|digit-normalized msg\|occurrence) | `[i/N] Processing` progress: no files gives `empty-scope`, and `i<N` gives `truncated-report`. Crash markers (Stack dump, Segmentation fault, LLVM ERROR...) and `clang-diagnostic-error` give `scanner-error`. Fewer files than `scope_minimums` gives `scope-mismatch`. |
| cppcheck XML v2 | `line-tool` for error/warning/portability; `cppcheck-bucket:<id>:<path>` counts for style/information | Not XML v2 or no version gives `invalid-report`. Zero `<error>` entries gives `empty-scope`. `internalError`, or a `checkersReport` saying "critical errors", gives `scanner-error` (marker `critical-errors`). |
| eslint JSON or stylish job log | `eslint-bucket:<rule>:<path>` counts | JSON `[]` gives `empty-scope`. A fatal parse message gives `scanner-error`. For the log, a parsed count different from the `✖ N problems` summary gives `invalid-report` (no partial parse). "Oops! Something went wrong" gives `scanner-error`. |
| npm audit JSON (all + prod) | `npm-audit:<lockfile>:<pkg>:<GHSA>` | An `error` key gives `scanner-error`. `dependencies.total==0` gives `empty-scope`. A build-only finding seen in the prod audit gives `exposure-escalation`. |
| Dependabot / Code Quality / advisories / secret scanning REST JSON | T1 sca / code-quality / `repo-advisory:sha256(GHSA)` / `secret:<type>:alert-<n>` | An API error body (`{"message","status"}`, such as the 404 for disabled secret scanning) gives `scanner-error`, never an empty result. |
| Sanitizer ctest log | gate | Sanitizer marker or failed tests gives `gate-failed`. 0 tests gives `empty-scope`. No summary gives `invalid-report`. |

**Comparison.** Findings are compared by identity, never by net counts:
- Any observed fingerprint missing from the inventory gives `new-finding`.
- Any bucket count above its baseline gives `bucket-increase`, and an unknown bucket gives `bucket-new`.
- These failures are reported even when other findings disappear or other buckets shrink.
- Disappearances are informational only: `resolved` / `bucket-decrease`. If the scan was partial, the label is `unobservable-partial-scan`. T1 `codeql-alert:<n>` identities are labelled `unobservable-identity`.

**Exceptions.**
- Inventory dispositions must exist in the policy `dispositions` table, otherwise `inventory-error`.
- Exception dispositions (`baseline-debt`, `exception-dismissed-false-positive`) must have `exception_expiry`; unbounded exceptions are an `inventory-error`.
- `today > expiry` gives `expired-exception`, whether or not the finding is still present. The expiry date is the last valid day.
- `--today` makes the date injectable.
- Duplicate fingerprints and unknown `scanner_id`s are also `inventory-error`.

**Exit status.**
- If `run-manifest.json` exists, a recorded `status` other than success gives `scanner-error`. So does an `exit_code` outside `accepted_exit_codes` (default `[0]`; `[0,1]` for npm audit, because exit 1 only means findings exist).
- The manifest also supplies `files_scanned` (0 gives `empty-scope`), `tool_version`, `db_version` and `revision`.
- Report contents are always checked too, so neither an exit-code mistake nor a "success" status can override an error recorded in a report.
- The checker's own exit codes:

  | Code | Meaning |
  |---|---|
  | 0 | pass |
  | 1 | policy failure |
  | 2 | usage error or unreadable input (argparse, missing reports dir/inventory/policy) |
  | 3 | internal error; traceback printed, plus `RESULT: ERROR - internal checker failure` |

- Malformed report structure becomes an `invalid-report` failure for that scanner, not a crash. Nothing is caught and turned into exit 0.

**Provenance.**
- Each scanner line prints tool name, version, query packs, DB version and revision. Values come from the SARIF driver/extensions/versionControlProvenance, the cppcheck version attribute, Trivy imageID, or the run manifest.
- A version different from `scanners.json` `tool_version` (or `db_version`) is listed under `PROVENANCE CHANGED <scanner>: tool_version A -> B`. It is visible but does not fail.
- If no version is available, the output says `version not recorded in report`. That currently applies to clang-tidy, and to the Trivy DB version until T14 records it.

**Renames.**
- Identity does not depend on line numbers. Real-data check: CodeQL analyses at `1b8d4332` and `8927bc8a` have 34/35 results shifted +7 lines by the SPDX headers, and fingerprints are identical. Both pass.
- Paths are part of identity. A path rename only keeps identity through an explicit, reviewed `path_renames` entry in the policy: `{from: inventoried path or dir/, to: current path or dir/, reason, approved_by}`.
- Observed paths are mapped back to `from` before fingerprinting, and every mapping is printed as `renamed`.
- Without an entry, a renamed file produces new findings, while the old ones show as resolved.
- After an explicit baseline edit rewrites the inventory paths, remove the map entry.
- The prefixes `/__w/lightNVR/lightNVR/` and `/home/runner/work/lightNVR/lightNVR/` are stripped.

**Accepted coverage gaps.**
- A gap is an entry in `accepted_gaps`: `{scanner, condition, [marker], [reports_dirs], owner, expires, reason, coverage_gap_ref, status}`.
- It downgrades one specific coverage issue to `ACCEPTED GAP <scanner>: NOT SCANNED|REPORT MISSING|SCANNER ERROR ...`, which is printed separately and never reported as a clean or valid-empty result.
- A gap without owner or expiry gives `policy-error`. An expired gap fails as the original condition with `[accepted gap expired ...]`.
- `--release` ignores all gaps. It also fails present findings whose disposition is `release_blocking`: `needs-triage`, `private-triage-pending`, `fixed-upstream-verify-regression`.
- All 4 gaps and their owners/expiries are `proposed-by-T6` and need maintainer confirmation.

**Baseline edits.**
- `--check` never writes. A test verifies the inventory sha256 is unchanged after a failing check.
- `--update-baseline --reason TEXT` is the only writer. It refuses while any coverage/config failure exists, so a missing or crashed report cannot be baselined.
- It adds new findings as `needs-triage` with no expiry, adjusts bucket counts, and removes resolved records only for fully observed scanners. It does not touch expired exceptions.
- It appends a `baseline_edits` record (date, reason, reports dir, added, removed, bucket changes) and writes in the T1 one-record-per-line layout.
- `--check` and `--update-baseline` are mutually exclusive (exit 2).

**Known limits.**
- With occurrence-index identity, if one of two diagnostics with the same rule, path and normalized message moves within a file, nothing new is reported. That is equivalent to a per-file bucket.
- For CodeQL SARIF from the REST API, a non-empty scope cannot be proven when there are zero results unless the run manifest provides `files_scanned`; the checker therefore fails such a report as `empty-scope`.
- GitHub REST alert lists cannot prove scope. An empty list is accepted as a valid empty result when the API returned 200.
