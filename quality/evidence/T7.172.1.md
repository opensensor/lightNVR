# T7.172.1 — bulk tag state during delayed recording refresh

The bulk overlay now retains successful local tag edits while recording rows are
still stale, independently of autocomplete catalog updates. A new recording
snapshot or selected-ID set recomputes all/some/none state, including same-count
refetches and replacement selections. A request completing after the selection
changes cannot mark the new selection as successfully updated.

This evidence supersedes the open bulk-tag defect recorded by T7.172; its
name-only commit remains separate.

Only BulkTagsOverlay reconciliation changed. RecordingsView remains unchanged:
its bulk `handleTagsChanged` callback invalidates the recordings query; the overlay
must tolerate the resulting delay. Existing API payloads, localization, pending
controls, callbacks and single-recording behavior remain. No backend, baseline,
exception, dependency or locale change.

## Cause and correction

Previously, the effect depended on `allTags` and `selectedRecs.length`. A successful
new-tag operation marked the tag all, then updated `allTags`. That update caused
the effect to recalculate from stale recording props, making the tag unchecked.
Same-count refreshed rows or a same-size replacement selection did not necessarily
re-run the effect.

Catalog merging now adds only unknown names as unchecked and preserves existing
states. A separate effect depends on the actual `recordings` snapshot and a stable
serialized selected-ID list, so a newly allocated selection object with identical
IDs does not reset local state. That effect treats newly delivered rows as
authoritative and recomputes known tags from selected recordings. Successful local
state is not a permanent override of later server data. A current-selection ref
checks the selection captured by asynchronous requests before applying their
local success state. The callback still runs so the real parent refreshes data.

## Behavioral coverage

- New-tag success remains checked with stale rows and after a later catalog response.
- Same-count refreshed rows recompute all/some/none states, including a later
  external removal from one selected recording.
- Same-size selection replacement and narrowing use actual selected rows; an
  old-selection request completing later does not mark the replacement selection.
- Exact add/remove/new-tag payloads preserve selected IDs and trimmed names.
- Pending fields/checkboxes are disabled; another native activation does not send
  a duplicate request.
- Failed mixed-tag add, all-tag removal and new-tag requests preserve the prior
  state and entered text, without success callbacks/messages or new checked tags.
- Subsequent successful add/remove operations recover correctly and invoke the
  original callback once per successful request.
- Existing name, keyboard, Escape, auth, settings, API and media-boundary controls
  remain in the related regression run.

The tests use fixture API promises and recording snapshots, not real recordings
or a running backend. They explicitly model the actual parent's delayed refresh
contract; they do not replace the missing delay with immediate updated props.
