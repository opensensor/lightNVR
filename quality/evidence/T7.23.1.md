# T7.23.1 — migration statement boundaries

The parser now tracks SQLite string and identifier delimiters separately,
including double-quote/backtick escaping and bracket identifiers. Line and block
comments cannot affect delimiters or trigger BEGIN/CASE/END depth. This fixes
the original valid-identifier failure and both UP/DOWN validation failures.
The allowlist itself is unchanged; validation still precedes execution of the
whole input. This is a bounded lexical fix, not a claim that all allowed SQL is
safe against every possible database configuration.

Four additional controls were written before production changes: backtick and
bracket identifiers, inline comments/escaped strings, and a quoted trigger name
with nested CASE. Actual expanded RED is native-6b5c2c31877b:13 cases/8 failures.
After the fix, native-e9800451a925 has13 cases/1 failure: all seven boundary
failures are green; only the separately scoped tracking-name failure remains.
All seven existing T7.2 migration-policy cases pass in both runs. No sanitizer
diagnostics appeared. Artifacts live under build/eng-artifacts/T7.23/, including
commands, source hashes, full failure logs and final LastTest.log. Both runs use
`python3 scripts/quality/run-native.py --task T7.23 --regex '^test_(t7_23|t7_2_migrations)$' --jobs 4`.

Only disposable in-memory databases/private fixtures were used. No service,
operator data, baseline, exception or scanner result was changed. The original
producer remains committed as87e55150; tracking-table correction is T7.23.2.
