# T7.26.2 — retain abandoned filesystem destinations with unknown ownership

Abandoned-job cleanup no longer unlinks an unregistered final filesystem
destination solely because a failed/cancelled job names it. The schema does not
persist proof that such a job published that inode. Existing regular files,
symlinks and other entries are therefore retained and reported for inspection;
matching contents alone do not establish ownership. No schema or storage policy
redesign was introduced, and automatic orphan reclamation is not claimed.

The bounded change is in `cleanup_abandoned()`. A destination already referenced
by a recording/retained copy remains protected. A genuinely absent unowned final
path permits normal cleanup completion. Unknown catalog state or failed pathname
inspection leaves cleanup pending. A present unowned entry is logged and its
reason is persisted in `last_error`, with `artifacts_cleaned` still false and the
existing retry delay. Existing failed/cancelled job state is preserved. S3 object
cleanup policy is unchanged; the error persistence uses the existing error
buffer rather than discarding its explanation.

The original committed producer demonstrates the cause independently: the first
pass rejects a preexisting destination collision, but the old second pass deletes
that unrelated file. Tests added before this fix cover an unowned symlink,
cancelled job, equal-content but unowned file, failed inspection, and a cancelled
job with no artifacts that should still complete cleanup. All originals remain.
